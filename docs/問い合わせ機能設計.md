# 問い合わせ機能設計書

## 1. 目的

企業担当者からの採用、面談、インターン、説明会、産学連携に関する相談を学校が安全に受け付け、担当教員が対象学生へ取り次げるようにする。

学生個人の連絡先は企業へ公開せず、学校を唯一の連絡窓口とする。

## 2. 設計方針

- 閲覧時のログインは要求せず、問い合わせ時だけ企業・担当者情報を取得する。
- MVPでは問い合わせ内容をサーバー上のJSONファイルへ保存しない。学校宛て通知メールを受付記録の正本とする。
- 入力、確認、完了の3段階とし、確認前および入力エラー時に送信しない。
- JavaScriptが無効でも、PHPのみで入力・確認・送信を完了できるようにする。
- 学生ID・チームIDは表示名ではなくIDで引き継ぎ、送信時に公開中データとの整合性を再確認する。
- メール送信の成否が不明な状態で「送信完了」と表示しない。

## 3. 対象範囲

### 3.1 MVPに含める機能

- 問い合わせ入力
- 入力内容の確認
- 学校窓口への通知メール
- 問い合わせ者への受付自動返信
- 送信完了画面
- 入力検証、CSRF対策、スパム対策、二重送信対策
- 学生詳細・チーム詳細から対象を引き継ぐ導線

### 3.2 MVPに含めない機能

- 問い合わせ履歴の管理画面
- 対応状況（未対応、対応中、完了）の管理
- ファイル添付
- 面談日時の予約
- 学生への直接メール送信
- CRM、Google Sheets等の外部サービス連携

履歴・ステータス管理は、個人情報をJSONで管理せずに済むデータベースと管理権限を準備した後のフェーズ2とする。

## 4. 利用者と権限

| 利用者 | 操作 |
|---|---|
| 企業担当者 | フォーム入力、確認、送信 |
| 学校窓口担当者 | 通知メールの確認、企業への返信、学生への取り次ぎ |
| 学生 | システム上の操作なし。学校から必要な範囲で連絡を受ける |

## 5. 画面設計

### 5.1 画面遷移

```text
学生詳細 / チーム詳細 / 共通ナビ
               ↓
          問い合わせ入力
          ├─ 入力不備 → 入力画面にエラー表示
          └─ 正常 → 確認画面
                       ├─ 修正 → 入力画面
                       └─ 送信 → 完了画面
                                  └─ 再読込しても再送しない
```

### 5.2 URLとHTTPメソッド

| 処理 | URL | メソッド |
|---|---|---|
| 入力画面表示 | `contact.php?student={id}` または `contact.php?team={id}` | GET |
| 入力検証・確認表示 | `contact.php` | POST |
| 送信確定 | `contact.php` | POST |
| 完了画面表示 | `contact.php?completed={受付番号}` | GET |

送信後はPOST結果を直接表示せず、完了画面へリダイレクトするPost/Redirect/Get方式とする。

### 5.3 入力画面

現在のデザインと以下の5つの目的を維持する。

1. 学校の先生に連絡したい
2. 説明会の相談をしたい
3. この学生と話をしたい
4. この学生に応募してほしい
5. この学生に注目している

学生・チーム詳細から遷移した場合は、対象を変更できない要約として表示する。自由入力の「対象の作品・学生」は廃止し、対象IDと補足メッセージを分離する。共通ナビから遷移した場合は対象なしで送信できる。

### 5.4 確認画面

- 入力値をすべてエスケープして表示する。
- メールアドレス、対象、問い合わせ目的を特に見つけやすく表示する。
- 「入力内容を修正する」と「この内容で送信する」を配置する。
- 送信確定ボタンは連打できない表示とする。ただしサーバー側でも二重送信を防ぐ。

### 5.5 完了画面

- 受付完了、受付番号、自動返信メールの送信先を表示する。
- 学校からの返信目安を表示する。目安は運用担当者が決定する。
- メールが届かない場合の確認事項を表示する。
- 入力内容そのものはURLや完了画面へ再表示しない。

## 6. 入力項目

| 項目 | 内部名 | 必須 | 制約 |
|---|---|:---:|---|
| 問い合わせ目的 | `action` | ○ | 定義済み5値のいずれか |
| 企業名 | `company` | ○ | 1～100文字 |
| 部署名 | `department` |  | 100文字以内 |
| 役職 | `position` |  | 100文字以内 |
| 担当者名 | `name` | ○ | 1～100文字 |
| メールアドレス | `email` | ○ | 254文字以内、メール形式 |
| 電話番号 | `phone` |  | 30文字以内、数字・空白・`+()-`のみ |
| 企業Webサイト | `website` |  | 2048文字以内、`https` URLを推奨 |
| 希望連絡時期 | `preferred_time` |  | 100文字以内 |
| メッセージ | `message` | ○ | 10～3000文字 |
| 対象学生ID | `student_id` |  | 存在し、公開中の学生ID |
| 対象チームID | `team_id` |  | 存在するチームID |
| 個人情報取扱い同意 | `privacy_agreed` | ○ | 同意済みであること |

`student_id` と `team_id` は同時指定を不可とする。前後の空白を除去し、改行コードを統一してから文字数を判定する。HTMLタグは許可しない。

### 6.1 目的と対象の整合性

- 「この学生と話をしたい」「この学生に応募してほしい」「この学生に注目している」は、対象学生を必須とする。
- 学生以外を対象に上記目的が選ばれた場合は、入力画面で目的変更を求める。
- 対象学生が送信までに非公開となった場合は送信を止め、「対象情報が更新されたため確認してください」と表示する。

## 7. 処理設計

### 7.1 入力から確認まで

1. セッションを開始し、CSRFトークンを発行する。
2. GETの対象IDをマスターデータで検証し、表示用の対象名を取得する。
3. POSTされた全項目をサーバー側で検証する。
4. エラーがある場合は入力値を保持して入力画面へ戻す。
5. 正常な場合は正規化済み入力値をセッションへ一時保存し、確認画面を表示する。

### 7.2 送信確定

1. CSRFトークン、確認用ワンタイムトークン、送信間隔を検証する。
2. セッション内の入力値を再検証する。
3. 対象学生・チームの存在と公開状態を再確認する。
4. 推測困難な受付番号を発行する。例：`TGS-20260827-A7K4P2`。
5. 学校窓口へ通知メールを送る。
6. 学校宛て送信に成功した場合のみ、問い合わせ者へ自動返信を送る。
7. セッションの入力値とワンタイムトークンを破棄する。
8. 完了画面へリダイレクトする。

学校宛て通知に失敗した場合は完了扱いにせず、入力内容を保持したまま再試行案内を表示する。自動返信だけが失敗した場合は受付自体を成功とし、サーバーログへエラーを残す。

## 8. メール設計

### 8.1 学校窓口向け通知

- 件名：`[TGS SCOUT][受付番号][目的] 企業名 / 対象名`
- From：サイト専用の同一ドメイン固定アドレス
- Reply-To：問い合わせ者のメールアドレス
- To：学校の問い合わせ窓口
- 本文：受付番号、受付日時、目的、企業・担当者情報、対象ID・対象名、希望時期、メッセージ

問い合わせ者の入力値を `From` や件名へ無加工で使用しない。ヘッダーインジェクション対策として改行を拒否する。

通知先は環境ごとに設定し、複数のメールアドレスを登録できるようにする。

| 環境 | 通知先 |
|---|---|
| デモ環境 | `krc24a11@st.itc.ac.jp` |
| 本番環境 | 学校が指定する1件以上のメールアドレス |

本番の複数宛先は、アプリケーション設定上ではメールアドレスの配列として扱う。受信者同士へアドレスを公開する必要がない場合は、1通のTo/Ccに列挙せず宛先ごとに個別送信する。全宛先をソースコードへ直書きせず環境変数等で管理する。

### 8.2 問い合わせ者向け自動返信

- 件名：`【TGS SCOUT 2026】お問い合わせを受け付けました（受付番号）`
- 学校が受け付けた旨、受付番号、問い合わせ概要、返信目安、心当たりがない場合の案内を記載する。
- 学生個人の連絡先は記載しない。
- 自動返信メールへ機密情報を過剰に転載しない。メッセージ本文は原則として全文掲載しない。

### 8.3 送信方式

本番は認証付きSMTPを推奨する。PHPの `mail()` を直接利用するかは学校サーバーの制約確認後に決定する。認証情報、送信元、宛先はソースコードへ直書きせず環境変数で管理する。

SMTPは、Webサイトからメールサーバーへメールの配送を依頼するための仕組みである。実装前に次の情報を学校またはサーバー管理者へ確認する。

| SMTP設定 | 内容 | 例 |
|---|---|---|
| SMTPホスト名 | 接続先のメールサーバー | `smtp.example.ac.jp` |
| ポート番号 | SMTP接続に使用する番号 | `587`、`465` |
| 暗号化方式 | 通信の保護方式 | STARTTLS、TLS |
| 認証の要否 | ID・パスワードが必要か | 必要／不要 |
| SMTPユーザー名 | 認証に使うアカウント | サーバー管理者指定値 |
| SMTPパスワード | 認証に使う秘密情報 | サーバー管理者指定値 |
| 送信元アドレス | Fromとして使用可能なアドレス | `tgs-scout@example.ac.jp` |
| 送信制限 | 1時間・1日あたりの上限等 | サーバー管理者指定値 |

パスワードは設計書、Git、公開ディレクトリへ記載しない。

## 9. セキュリティ・スパム対策

- POSTのみで送信し、CSRFトークンを検証する。
- 確認画面ごとのワンタイムトークンで二重送信を防ぐ。
- セッションCookieに `HttpOnly`、`Secure`、`SameSite=Lax` を設定する。
- HTTPSを必須とする。
- 出力時にHTMLエスケープし、メール本文では制御文字を除去する。
- ハニーポット項目と、フォーム表示から送信までの最短時間判定を導入する。
- 同一セッションおよびIPアドレス単位で送信頻度を制限する。
- bot被害が確認された場合にTurnstileまたはreCAPTCHAを追加できる構成にする。
- エラー画面にSMTP情報、例外内容、サーバーパスを表示しない。
- アクセスログやエラーログへ本文、電話番号、メールアドレスを平文で出力しない。

IPアドレスを制限判定に使う場合、永続保存は避け、必要なら秘密鍵付きハッシュを短期間だけ保持する。

## 10. 一時データ・ログ設計

### 10.1 セッション一時データ

```text
contact.form_data       正規化済み入力値
contact.csrf_token      CSRFトークン
contact.submit_token    確認画面用ワンタイムトークン
contact.started_at      フォーム表示日時
contact.completed_id    直近の受付番号
```

送信成功後または一定時間経過後に削除する。

### 10.2 アプリケーションログ

保存可能な項目は受付番号、処理日時、成功・失敗、失敗工程、例外分類に限定する。問い合わせ本文などの個人情報は保存しない。ログの閲覧権限と保存期間はサーバー運用規程に合わせる。

## 11. 運用フロー

1. 学校窓口が通知メールを受信する。
2. 受付番号を基準に内容を確認する。
3. 対象学生への共有可否と共有範囲を判断する。
4. 企業担当者へ学校窓口から一次返信する。
5. 必要に応じて学生・教員・企業間の日程を調整する。

宛先メールボックスには複数の学校担当者がアクセスできるようにし、休暇・不在時の代替担当を決める。迷惑メールフォルダーも定期確認する。

## 12. エラー設計

| 状況 | 利用者への表示 | システム動作 |
|---|---|---|
| 入力不備 | 項目直下と画面上部に具体的なエラー | 入力値を保持 |
| セッション期限切れ | 入力画面からやり直す案内 | トークンを再発行 |
| 対象が非公開・削除済み | 対象を再確認する案内 | 送信しない |
| 学校宛てメール失敗 | 時間を置いた再試行と代替窓口の案内 | 完了扱いにしない、技術ログを記録 |
| 自動返信のみ失敗 | 受付済みである旨を表示 | 受付成功、技術ログを記録 |
| 連続送信・bot判定 | しばらく待って再試行する案内 | メールを送らない |

## 13. テスト観点・受入条件

- 5種類の目的を正常に送信できる。
- 学生詳細・チーム詳細から正しい対象IDと対象名が引き継がれる。
- 必須、文字数、形式、不正な選択値、存在しないIDをサーバー側で拒否する。
- HTMLや改行を含む入力で画面表示・メールヘッダーが破壊されない。
- CSRF不正、確認画面を経ない送信、同一トークンの再送を拒否する。
- ブラウザの戻る・再読込・送信ボタン連打で重複メールが発生しない。
- 学校宛て通知と自動返信の件名・本文・文字化け・Reply-Toを実メール環境で確認する。
- SMTP障害時に完了画面を表示しない。
- スマートフォンでエラー箇所、確認内容、完了案内を読みやすく操作できる。
- JavaScript無効時にも送信できる。
- 個人情報がURL、HTMLソース、一般ログへ残らない。

## 14. 実装前に確定する事項

1. 本番環境の通知先メールアドレス一覧と、宛先ごとの個別送信要否（デモ環境は `krc24a11@st.itc.ac.jp`）
2. 送信元アドレス、SMTPホスト名、ポート、暗号化方式、認証の要否、認証情報、送信制限
3. SPF、DKIM、DMARCの設定可否
4. 学校からの一次返信目安
5. 問い合わせメールと技術ログの保存期間
6. 利用するスパム対策サービスの有無
7. プライバシーポリシーに記載する運営主体、連絡先、保存期間、開示等の請求方法
8. フェーズ2で履歴管理を必要とするか、その場合のデータベースと管理者権限

## 15. フェーズ2案：履歴・ステータス管理

必要性が確認された場合に、認証付き管理画面とデータベースを追加する。問い合わせレコードには受付番号、入力項目、受付日時、ステータス、担当者、最終更新日時を保持し、ステータスを `未対応`、`対応中`、`完了`、`対象外` とする。

この段階では、保存期間経過後の自動削除、操作履歴、CSV出力権限、バックアップ、開示・削除依頼への対応も合わせて設計する。
